## 2. WP1: the static terrain minimap

Built in `CARGO_TARGET_DIR=/home/spacescuffle/cargo-target/minimap`; logs under `~/scratch/minimap/wp1/`.

- **Red first.** `minimap_tests.rs` with the WP1 sources stashed (base `a061052a`): 28 compile errors, every one a
  missing `client::minimap` API or the missing `HudGeometry::minimap` / `HudLayout::minimap` field
  (`red/minimap_tests.log`).
- **CPU** (`minimap_tests.rs`, 9 tests: M-1, M-2 on `showcase_canyon` and `default_arena` and the revision rule, M-3,
  M-11 sandbox, default layout and panel-less layout, the shader's naga validation): all pass. With the default layout
  the world viewport is `(0, 28, 1280, 512)` at 1280×720, the base commit's, and one image is created and none in the
  steady state.
- **GPU** (`minimap_gpu_tests.rs`, radv, RX 580): G-1 on the skirmish (level 3 over level 2 on metal plate: linear
  luminance 0.1419 against 0.1201, ×1.18 ≥ 1.10; unwalkable cells within 0.05 of `unpathable_color`; no black pixel on
  the map), G-1's letterbox on a 64×80 copy of the skirmish map (16 rows prepended in a temporary assets root), and G-6
  (24,438 flat texture pixels compared with the window shot inside `HudGeometry::minimap`, none differ by more than
  6/255). The window shot uses a test copy of `client_diagnostics`' egui screenshot attachment, without which Bevy
  0.15's screenshots show no egui.
- **Existing tests rerun:** client lib (`minimap`, `input_bindings`, `battle_hud` filters, 92), `battle_hud_tests` (35),
  `sync_steady_state_tests` (16), `battle_card_tests` (35), `workspace_checks`, `gate` `suite_catalog_tests`: all pass.
- **Simulation identity:** the plan's §5 `git diff --stat` from `a061052a` over the simulation crates and the
  simulation-read assets is empty.

Deviations: see the hand-back of WP1 and the plan's As built (written at WP5): the image keeps its bytes in the main
world (`RenderAssetUsages::default()`), because bevy_egui 0.33 drops the user texture of an image removed from the main
world; `MINIMAP_TERRAIN_KEY` is an Alt chord in a new `ALT_ACTION_KEYS` table, because `T` is a command-card key in
`ACTION_KEYS`, and the card ignores keys while Alt is held; `minimap_tests` is catalogued `Slow` with two threads,
like the HUD's tests, rather than the default class.

## 4. Budget (M-B1, M-B2), measured early at the WP2 hand-back

- **M-B1**, `cargo bench -p client --bench minimap_prepare` (release, `cargo-target/minimap-release`), the skirmish
  with 400 units added (414 bubbles, 227 marks listed under player 0's fog), median of 501 passes, three runs at a
  one-minute load of 7.8 on 2026-11-27 07:32 UTC: marks rebuild 7.04, 8.88 and 7.04 µs against the 200 µs bar; fog
  bytes 4.5 µs per refill; per-frame part 0.04–0.05 µs against 20 µs (the layout only: the frustum is WP3's).
- **M-B2**: `frame_budget` runs `ClientMode::LiveBattle`, the sandbox profile, which has no HUD and no minimap (the
  plan's T16 is mistaken), so it cannot attribute the minimap pass without a behaviour change the plan rules out. The
  pass's GPU time was measured instead in the G-2/G-3 child with Bevy's `RenderDiagnosticsPlugin` and the node's
  `minimap` pass span, on the RX 580 under the shipped skirmish with the clock running: mean 0.0046 ms, median
  0.0045 ms, max 0.0054 ms over 60 frames with 30 marks, against the 0.1 ms bar. The pass is one full-screen
  triangle on 172×172 pixels plus one instanced draw, so 400 units (a few hundred more quads) do not change its
  order of magnitude; WP5 can repeat it at 400 units once `frame_budget` can run the player profile.
