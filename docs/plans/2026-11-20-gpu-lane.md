# Blueprint: A Shorter GPU Lane for `cargo gate package` and `full`

A package gate whose change selects the client's GPU targets takes 50 to 60 minutes, and almost all of it is the
test phase. The GPU lane decides that phase: in the two gates of record that ran every GPU target (§2.1) it ran
2,784 and 3,283 s, while the two general lanes were done after 1,353 and 1,148 s. Plan `2026-11-17-gpu-test-readback`
halved the lane (Amendment 6) but left it the critical path by 21 to 24 minutes, and named the next candidates.

This plan:

- measures where the lane's time goes now, down to the phases of a child (§2);
- explains why no arrangement of lanes can take the lane below the GPU time of its children (§3);
- evaluates the four candidates the orchestrator named and the others the timings point to (§4);
- adopts three changes that keep every test and every check (§5):
  - the GPU lane starts with the valgrind jobs instead of after them (D-1);
  - once the general lanes run dry, a second GPU job may run, so the parents' own work overlaps the children
    (D-2);
  - `weapon_battle_gpu_tests` stages its subjects where there is room again, so its 23 one-subject waves become
    about 6 (D-3);
- fixes the harness so that GPU validation works in release builds (D-5);
- states before any measurement how each change is accepted, with metrics that load does not decide (§6).

**Expected effect** (estimate from the gates of record, §6.4): the test phase of the newest gate of record falls
from 3,660 s to about 2,200 s, about 24 minutes shorter (−40 %). The GPU lane stays the critical path, by about
10 minutes on a loaded host; §11 lists what is left.

**Status of this document:** a stage 1 blueprint under charter §6, written on 2026-11-20 against `main` at
`3ed2f768`. A full plan is required: the work spans packages (`gate`, the client's GPU harness and one GPU test),
changes how every package and full gate schedules its tests, and changes a test that guards a battle look.

### 2.4 Profiles

`perf record -F 99` (`-F 499` for the client), no call graphs, self time per symbol, each symbol assigned to the
crate its code was generated in (the instantiating crate of a generic, the last crate in its v0 symbol), because
that crate's opt-level is the one that ran.

- **Slice children** (offscreen, so `perf` follows them): libc 22.8 % (`memmove` alone 16.4 %), code generated in
  `client` 20.9 %, the kernel 8.6 %, the validation layer 7.5 %, `fdeflate` 3.5 %, `bevy_ecs` 2.7 %. Of `client`'s
  share, about 13.5 points are the lab's PNG encoder (`effects/lab/driver.rs`, `write_png`): `PngEncoder` and
  `fdeflate`'s compressor are generic over the writer, so they are instantiated in `client` and run at opt-level 0.
  Another 3.4 points are the debug precondition checks of `from_raw_parts` and `ptr::copy`.
- **Skirmish start-up**, as a proxy for a windowed child (`client --skirmish --max-frames 60` with
  `WGPU_VALIDATION=1`, under Xvfb with `MESA_VK_WSI_DEBUG=sw` because `perf` cannot follow a KWin child): 25.3 s
  wall, user 16.5 s, sys 11.4 s. The kernel 42 % (the software present's copies, which a KWin child does not pay),
  `client` 12.6 %, PNG decoding of the media (`fdeflate` 8.0 %, `png` 6.5 %, both at opt-level 2), libc 7.8 %,
  the validation layer 5.5 %.
- **KWin children cannot be profiled.** `kwin_wayland` carries the file capability `CAP_SYS_NICE`
  (`security.capability` = `0x800000`), and an exec of a binary with file capabilities stops `perf`'s inheritance:
  of the weapon run's 2,200 samples, 2,130 came from the parent's test thread and none from a child. The parent's
  own work in that run was about 21.5 s of CPU. So a KWin target's CPU is read from `rusage` of the whole process
  tree (each process waits for its children, so the counts reach the parent), not from `perf` (§6.1).

### 2.5 The valgrind phase

| Job | Wall | Peak (estimate) | Class |
|---|---:|---:|---|
| `client/sync_allocation_count_tests` | 184 to 255 s | 36.4 to 38.3 GiB | valgrind |
| `sim_core/effect_tree_allocation_tests` | 101 to 128 s | 76 to 85 MiB | valgrind |
| New targets with no recorded peak (for example `sim_core/harvest_edge_tests`, 49 s) | 0 to 49 s | — | alone |

- Both valgrind targets count allocations in windows chosen by call stack, on single-threaded schedules, over
  fixed frame counts, and assert that two runs at the same frame count give the same count
  (`sync_allocation_count_tests.rs`, module doc). Their counts do not depend on load or wall time. Plan
  `2026-11-11-faster-gates` made them exclusive because their children use up to one core each (D-4) and so the
  counts would not be skewed by other load (L-2); the second reason does not hold for these targets.
- The default memory budget of the lanes is 40 GiB of estimates (`DEFAULT_MEMORY_BUDGET_MIB`), and the live ceiling
  is the cgroup's limit less 10 GiB. Beside `sync_allocation_count_tests` (36.5 GiB), a job of at most 3.5 GiB fits
  the budget: `effect_slice_gpu_tests` (about 300 MiB), `capture_path_gpu_tests` and the two decal targets
  (about 250 to 330 MiB) do, the skirmish GPU targets (4.2 to 4.6 GiB) do not.

### 2.6 GPU validation in release builds

`docs/evidence/2026-11-20-tastar-budget.md` (Amendment 2) observed that in a release build 13 GPU targets fail
their validation children with "VK_LAYER_KHRONOS_validation was not inserted", and that all pass in debug. Cause,
traced in the sources of `Cargo.lock`'s versions:

- Bevy 0.15.3 builds its instance flags as `InstanceFlags::default().with_env()` (`bevy_render/src/settings.rs`).
- In wgpu-types 23.0.0, `InstanceFlags::default()` is `from_build_config()`, which is `DEBUG | VALIDATION` only
  under `debug_assertions` and empty in release. `with_env()` reads `WGPU_VALIDATION` and `WGPU_DEBUG` separately.
- In wgpu-hal 23.0.1 (`vulkan/instance.rs`), `VK_EXT_debug_utils` and its messenger are enabled only with `DEBUG`.
  The messenger is the only path by which the layer's and the loader's messages reach the log.
- The harness sets `WGPU_VALIDATION=1` only (`GpuCommand::run_validated`). In release the layer is requested, but
  without the messenger the loader's "inserted" message never reaches the log, and the harness's invariant (a run
  counts as validated only if the loader reported inserting the layer) fails the run, as it should.

The fix belongs in the harness: set `WGPU_DEBUG=1` beside `WGPU_VALIDATION=1` (D-5). It is not on the gate's path
(the gate builds debug), so it shortens nothing. It is in this plan, as a work package of its own (WP2), because a
change to `gpu_run.rs` selects every GPU target: sharing a package with WP1, whose change selects the complete suite
anyway, it costs no gate of its own.

## 3. Diagnosis

1. **`T = X + R`, and `X` is pure delay for the GPU lane.** The GPU lane waits for the valgrind jobs, which share
   neither the GPU nor, except for one job, much memory with it.
2. **`R ≥ C + external lock waits`.** The lock admits one child at a time (charter §7), so no number of GPU lanes
   takes the lane below the time the children hold the GPU. A split of a target changes nothing in `C`.
3. **The part of `R` that is not `C` can overlap `C`** if a second GPU binary runs: while one binary compares its
   pictures, opens its next child or runs its in-process tests, another binary's child holds the GPU. In
   `33b3fd5f` that part is 459 s, and the general lanes that could run it are idle from 1,526 s on.
4. **`C` itself has one large fixed cost:** `weapon_battle`'s 46 client start-ups (685 s of 876 s). The lab
   children are frame-bound, so their count matters little. The windowed children of the other targets pay a
   start-up each too, but one to three per target, each for a different picture.

So the plan moves the GPU lane's start to zero (D-1), overlaps the non-child work once the general lanes are empty
(D-2), and removes most of `weapon_battle`'s start-ups by staging its subjects where the screen has room (D-3).

## 4. Candidates evaluated

1. **Merge each slice subject's three children** (setup evaluation 7(d)). The split into halves was made when each
   child ran about 80 s under Xvfb, to stay inside the 120 s run limit; offscreen they take 7 to 25 s, so a merged
   child (about 40 s on radv, about 100 s on CI's lavapipe) would fit. But the gain is at most about 45 s of a
   1,000 s target whose run-to-run spread was 289 s (WP5: 716 and 1,005 s). Not adopted (§11).
2. **The GPU lane during the valgrind phase** (setup evaluation 7(c)). Adopted as D-1. Memory decides what can run
   beside `sync_allocation_count_tests`; the slice, the longest GPU job, fits.
3. **Split or slim the largest GPU targets.** A split adds a binary and a lane slot but no GPU time, so it cannot
   shorten a lock-bound lane, and it adds a binary to `gate/selection_tests`' count of GPU binaries. Slimming
   `weapon_battle` by restaging its waves (D-3) removes 32 to 34 of its 46 start-ups with the same subjects and
   checks. The slice's slimming is candidate 1.
4. **Other changes the timings point to.**
   - (a) A second GPU job once the general queue is empty: adopted as D-2. More than two would not shorten a
     lock-bound lane further and would lengthen every child's lock wait.
   - (b) Release validation: adopted as D-5 (§2.6).
   - (c) Code generated in `client` runs at opt-level 0 (`Cargo.toml` raises only dependencies, `sim_core`,
     `sim_map` and `asset_baker`); in lab children that is mostly the PNG encoder. Two fixes are possible: a
     non-generic encoding path generated in a dependency, or `[profile.dev.package.client] opt-level`. The second
     changes compile time of every client build and the first is a production change in the lab writer; both
     deserve their own A/B. Not adopted (§11).
   - (d) The slice's 44 shot and 24 look children are frame-bound lab children too; merging them needs a lab program
     with several subjects (a production change in `client::effects::lab`). Not adopted (§11).
   - (e) Doc tests and golden replays run after the lanes (81 s in `33b3fd5f`); they could start in a free general
     lane during the GPU tail. Small, and plan `2026-11-11-faster-gates` D-7 kept them apart. Not adopted (§11).
   - (f) Validation on only some children, or lavapipe for functional targets: rejected. The first weakens a check
     (charter §1.2); the second was measured not to pay (Q0083, readback plan Amendment 6).

## 5. Design decisions

### D-1. The GPU lane runs during the valgrind jobs

Today `L-2` (`crates/gate/src/schedule.rs`) runs every exclusive job with nothing else running. It is split:

- **Alone jobs** (a job with no memory estimate, a target marked `exclusive: true`): unchanged. They run first, one
  after another, with every lane idle, the GPU lane included.
- **Valgrind jobs** then run one after another with every general lane idle, as today, but **the GPU lane is open**.
  A GPU job starts beside them only if its estimate plus the largest estimate among the valgrind jobs still running
  or waiting fits the budget, and the live reading plus its estimate fits the ceiling. Reserving room for the
  largest valgrind job means a valgrind job never waits for a GPU job to end.
- **The GPU queue may be overtaken** while the valgrind phase lasts: the GPU lane takes the longest GPU job that
  fits, as the general lanes already do (L-3), so a large skirmish target at the head of the queue cannot keep the
  slice waiting.
- The general lanes open when the last valgrind job ends, as today.
- One lane (`--jobs 1`, CI) is unchanged: every job runs alone, in order (L-1).

The valgrind counts are deterministic by construction (§2.5), so a GPU job beside them cannot change a count. It can
slow them, by one or two cores out of 16; that cost is measured in §6 and is small against `X`.

### D-2. A second GPU job once the general queue is empty

- When a general lane is free, the general queue is empty, and exactly one GPU job is running, the free lane may
  take the next GPU job that fits the memory limits. At most **two** GPU jobs run at once.
- In `lanes.tsv` and the progress lines that lane is named `GPU2`, so a GPU job can still be told from a general
  one by its lane.
- The children of the two binaries queue on the fair lock (Q0088). One child waits for at most the other binary's
  children ahead of it in the queue, each limited by the 120 s run limit, against the harness's 290 s lock wait.
- Nothing changes for the children: still one on the GPU at a time, each taking the lock itself (charter §7).
- Time limits (`time_limit`, four times the recorded wall or 15 minutes more) already leave room for a binary whose
  children wait for another's.

### D-3. `weapon_battle_gpu_tests` stages its subjects where there is room

The test's subject, families and checks stay as they are: every family of weapon looks fires in the production
client playing the shipped skirmish, on the shipped floor, **at the battle camera's default zoom**; each wave runs
as itself and as its blank; every subject is judged by the same rules and constants (`SEEN_PIXELS`,
`IMPACT_MARGIN`, `UNDER_ALLOWANCE`, `LAUNCH_TOLERANCE_PX`, `WAVE_SECONDS`, `SETTLE_SECONDS`); every child runs
under validation. What changes is where the camera looks when a wave is staged:

1. **The camera pans to open ground.** Before the spots are sought, the child moves the battle camera's target,
   without changing its zoom, from the start base towards the map's interior, to the first candidate target (by
   distance from the start location, in a fixed order) at which `find_spots` finds `MAX_SUBJECTS` spots, or else to
   the candidate where it finds the most. The candidates and the choice depend on the map, the catalog and the fog
   alone, so the parent and every child, the blank included, agree on them. The camera must be still again before
   the spots are sought, as at boot.
2. **What the viewer sees is checked when it matters.** A spot must still be seen when the wave fires: the staging
   asserts it for every subject's shooter and target at the baseline picture, and fails naming the subject if not.
   If panning within the base's sight cannot reach `MIN_SPOTS`, the search may admit spots the viewer will see once
   the wave's own shooters (the viewer's units) stand on them; the baseline assertion then still proves that
   nothing is pictured under fog. WP3 decides between these by the probe of its first step.
3. **A guard against the regression of §2.2.** A wave child that finds fewer than `MIN_SPOTS` (6) spots fails, and
   its message counts the candidates each condition rejected (the probe of §2.3, kept as a diagnostic). Any future
   map or clearance change that crowds the waves again fails at once instead of doubling the target's time.
4. **Expected shape.** With up to 9 subjects a wave, the 23 subjects of today plan into about 6 waves (the native
   families in 2, the lent ones in 1 or 2, the approach wave, and the two cross-plane waves, which stay alone
   because each packs three ground units), so 12 to 14 wave children instead of 46.

This restores the design the test was written for (9 subjects a wave, "as many a wave as the child finds spots
for"); Amendment 4 of the resource footprints plan was right to keep spots away from footprints, and that
clearance is kept.

### D-4. Every gate prints its GPU occupancy

The GPU block of the gate's report (`gpu_ledger.rs`, `RunReport::render`) gains one line: the time the gate's
children held the GPU (`C`), the test phase (`T`), and `η = C / T`. It is §6's metric, computed the same way in
every future gate, so the lane's health is visible without a script. It needs no new ledger field (§2.1).

### D-5. GPU validation works in release builds

`GpuCommand::run_validated` sets `WGPU_DEBUG=1` beside `WGPU_VALIDATION=1`. In debug both bits are already set, so
debug runs are unchanged; in release the debug messenger now exists, and the loader's messages reach the log
(§2.6). The module doc's "How validation reaches this module" says so. The observation becomes a bug of the
register, `DESIGN.md` §4 (the next free number: B-157 when this was written; B-159 as built, since the
contact-solver branch registered B-157 and B-158), fixed by this WP.

### D-6. What stays the same

- No test, child, check, golden or tolerance is removed or loosened. The GPU binary count stays 28 (25 in `client`,
  3 in `client_diagnostics`), so `gate/selection_tests` keeps deriving the set from the catalog; the stale comment
  on `MIN_GPU_BINARIES` ("21 client GPU binaries and 3") is refreshed to these figures, and the floor stays 20.
- No catalog rule or class changes, so no selection changes.
- The charter and its guides are unchanged.
- CI is unchanged: it runs one lane (`SPACE_SCUFFLE_GATE_JOBS: 1`), where neither D-1 nor D-2 applies. CI gains D-3
  (its `weapon_battle_gpu_tests` took 816 to 857 s on lavapipe).

### D-7. Measurement before acceptance

Each adopted change is accepted by the rules of §6, which are fixed here, before any of the measurements they
judge.

## 6. Acceptance, stated before measuring

### 6.1 Metrics, and why load does not decide them

| Metric | Source | Why it holds under load |
|---|---|---|
| `T`, the test phase | `lanes.tsv`: last end minus first start | Not robust alone; used only for its direction |
| `C`, GPU time held by the gate's children | Sum of `run_s` in the run's ledger | Exact work measure for a scheduling change, which leaves the children as they are |
| `η = C / T` | D-4's line | Load stretches `C` and `T` alike; a scheduling change moves `η` only by changing overlap |
| GPU lane's first start against the valgrind phase's end | `lanes.tsv` | Exact order, no timing |
| Children per target | Ledger line count | Exact |
| CPU of a target's process tree | `rusage` of the test process and its waited descendants (`bash`'s `time`: user + sys) | Contention inflates CPU time far less than wall time; used where `perf` cannot follow (KWin, §2.4) |
| Instructions retired, user space | `perf stat -e instructions:u` over the target, inheriting | Independent of contention; used for offscreen targets only |
| Load | One-minute load at each start and end; the `anon` line; `with-gpu-lock` holds of others | Recorded with every run |

## Amendment 1 (implementation agent, 2026-11-20, for the orchestrator's review): what WP3's probe and first trials decided

Recorded under Q0002 (scoping is the agent's call if written down); no acceptance rule of §6 changes.

1. **D-3 item 2: spots seen once staged.** The probe of WP3's first step, headless on the shipped skirmish after its
   first ticks (`the_camera_pans_to_ground_with_room_for_the_waves` prints it): at the boot target `(5.5, 5.5)` one
   spot of 336 candidates (open 294, sides 307, nodes 308, units 154, fog 75 rejections); at every candidate target
   within the base's sight at most 4 spots. So the waves admit spots outside the viewer's sight
   (`Sight::OnceStaged`): the fog is counted but rejects nothing, and the baseline picture asserts that every
   subject's shooter and target is in the viewer's sight (`assert_staged_units_seen`), failing with the subject's
   family and approach.
2. **A spot must be level** (a new condition of the spot search, `level`, `LEVEL_TOLERANCE` 0.05 world units). The
   first B trial staged waves round `(17.5, 5.5)`, where the base's plateau ends in a cliff: four subjects whose
   targets stood below the edge were hidden by the high ground and failed (`grenade_lob`, `needle_volley`,
   `rocket_trail` Across, `impaler_strike`). The probe of the 5 by 5 cells and the pair's ends at one height keeps
   every subject on one level; the search then pans to `(20.28, 11.62)`.
3. **Looks are attributed to the nearest subject** (`owner`). With several subjects a wave, two may fire the same
   look (`bullet_hit`, `rocket_hit`, `acid_hit` each serve two families). The old count (`spawned_of`, any instance
   of the look born) would let one subject's impact count for another. Each instance is now counted for the subject
   nearest to it that names its effect, from an impact's anchor to the target and from a travel's line start to the
   shooter. This makes the checks at least as strict as with one subject a wave.
4. **The parent checks the plan.** Every child must report as many waves as wave 0 (they plan from the spots they
   find, so a child that found a different number would stage different subjects).
5. **Expected shape, as built.** On radv the windowed children find 7 spots round `(20.28, 11.62)` (the headless
   search, which moves the boot camera's view by the pan, finds 9 there; the guard reads the real camera's), so the
   23 subjects plan into 7 waves: 14 wave children and the held beam, against 46 and the held beam.
6. **R-1's stamp directories are seeded.** A gate reads each target's timing and memory estimate from the stamps in
   its stamp directory, so a run with an empty `--stamp-dir` finds every target unmeasured and runs everything alone
   (the first R-1 attempt did; it was stopped at its fifth target, its logs kept under
   `~/scratch/gpu-lane/r1/aborted-A1-unseeded/`). Each of R-1's four runs starts from one snapshot of the default
   stamps (none of R-1's tree), copied into its own directory, so the four runs schedule from the same data and no
   run's stamp is seen by another.
