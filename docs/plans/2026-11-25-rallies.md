# Blueprint: Rally Slots, Rally Waypoints and Rallies on Enemy Units (B-164, B-165, B-166, B-167)

This plan finishes the rally of plan [`2026-11-23-production-queue`](2026-11-23-production-queue.md) (B-60), whose
D-11 registered four minor differences from StarCraft II 5.0.14:

- **Rally slots (B-164).** A production structure holds one rally per slot of its rally ability, and the slots are
  catalog data. Every structure has one slot, used by every unit it makes, except the Hatchery analogues. They get
  5.0.14's `RallyHatchery`, with two slots:
  - an army slot, used by non-workers, which cannot be set on a resource;
  - a worker slot, used by workers, which a right click on the ground does not set.

  The Queen analogue uses neither slot. A right click sets the first slot that takes the target. The card's
  rally entries set a named slot.
- **Rally waypoints (B-165).** Shift appends a waypoint to a slot's rally, up to a cap from data (4). A new unit gets
  one queued order per waypoint, so an SCV rallied through two points and then to a mineral field walks the route
  and then mines. A waypoint on a unit that has died is dropped, and the unit goes on to the next one.
- **Rally on an enemy unit (B-166).** The rally stores the enemy unit, not a point on the ground. A new unit that
  can attack it gets an attack order on it. One that cannot moves to where the enemy stands, which is the rule for
  a friendly unit until B-163's follow order exists.
- **Exit placement (B-167).** Nothing new was sourced. The row stays open as a recorded minor difference (D-9).
- **Found while planning (B-216):** a rally set on one's own extractor makes new workers walk to it instead of
  harvesting there. The client's right click now rallies to the extractor's node, as its unit orders already do.

A full plan is required (charter §6). This is a new mechanic (slots and waypoints), it changes the checksum format
(the rally becomes a list of routes), and it spans `sim_types`, `sim_core`, the catalog and the client.

### 2.2 The rules that follow

1. **A structure has as many rallies as its rally ability has `InfoArray` entries** (S1, S3). That is one for
   every producer, and three for the Hatchery, Lair and Hive, of which the third can never be set (`Failure`). The
   ability does not depend on the race: the Command Center and Nexus records change only a colour (S2).
2. **Which slot a new unit uses.** Each slot has use filters and use validators (S3): `-;Worker` for non-workers,
   `Worker;-` for workers, and `NotQueen` on both of the Hatchery's slots, so a Queen uses no rally (S5, S8: "the
   queen is independently created"). A unit uses the first slot whose use rule accepts it [INF, **verify**]. If that
   slot holds no rally, the unit gets no rally order, and the game does not fall through to a later slot [INF,
   **verify**; consistent with S7, where the auto-rally fills only a Hatchery's worker slot and its Overlords then
   stay put].
3. **Which slot a command sets.**
   - The card's button names its slot: `Rally1` is slot 0 and `Rally2` is slot 1 (S1, S6).
   - A right click (the smart command) sets the first slot whose set rule accepts the target.
     - The army slot refuses a resource (S4), so a right click on minerals sets the worker slot.
     - The worker slot has `SetOnGround 0`, so a right click on the ground sets the army slot. That is S8's split
       exactly ("right-clicking on a mineral cluster" against "elsewhere on the map").
   - `SetOnGround 0` does not stop the explicit worker rally on the ground: S8 says to rally drones "somewhere else
     on the map besides a resource node, press the G key and left-click". So the field governs only the smart
     command [INF from S3 and S8].
4. **A rally on an enemy unit is valid.** S4's validator names enemy targets as accepted. The default rally has no
   set validator at all (S1). S11 says the new unit gets an attack order on it.
5. **A rally on a friendly unit means follow** (S9, S11). That is B-163, which needs a follow order (§14).
6. **Rally waypoints exist.** Shift-clicking queues further rally targets. A new unit walks them in order and
   carries out the last one's meaning (mining at the end of a route, S10 post 25). A waypoint on a unit that has
   died is skipped (S10 post 1), and when every waypoint is gone the rally is cancelled (S10 post 35, S11, S9). The
   cap is "up to four" (S10 post 1) [COMM, Wings of Liberty, **verify** for 5.0.14]. What happens to a fifth
   Shift-click is not sourced (**verify**).
7. **The waypoints become the unit's orders.** A ground rally is a Move, not an attack-move (S11). A resource
   rally makes a worker harvest (S9), and a unit rally makes the new unit follow, attack (S11) or board (S9).
8. **Exit placement.** Nothing read here gives the engine's placement search. S12 (an analogy) and S9 ("set rally
   points on the structures' unobstructed sides") remain the only hints. B-167 stays as recorded (D-9).

## 4. Design decisions

### D-1. Rally slots are catalog data

- `sim_types` gains:

  ```rust
  /// A production structure's rally ability (StarCraft II 5.0.14 `CAbilRally`): its slots and how
  /// many waypoints a slot's rally holds.
  pub struct RallySpec {
      /// Most targets one slot's rally holds; Shift appends until then (B-165). At least 1.
      pub max_waypoints: u8,
      /// The slots in `InfoArray` order; slot `i` is the card's `Rally{i+1}`. At least one.
      pub slots: Vec<RallySlotSpec>,
  }

  /// One rally of a structure (`CAbilRally` `InfoArray` entry).
  pub struct RallySlotSpec {
      /// The card entry's text, from data (the button face's name).
      pub label: String,
      /// Which units use this slot (`UseFilters`): `All`, `Workers` or `NonWorkers`.
      #[serde(default)] pub used_by: RallyUsers,
      /// Unit slugs that never use it (`UseValidators`, e.g. `NotQueen`).
      #[serde(default)] pub excludes: Vec<String>,
      /// Whether it may be set on a resource node (`SetValidators NotResourcesOrEnemyTargetType`: false).
      #[serde(default = "default_true")] pub on_resources: bool,
      /// Whether a right click on the ground sets it (`SetOnGround`).
      #[serde(default = "default_true")] pub smart_on_ground: bool,
  }

  pub enum RallyUsers { #[default] All, Workers, NonWorkers }
  ```

  A worker is an archetype with a `HarvesterSpec` (T9). That is a capability, so no identity is named in code
  (charter §3.3). `excludes` names slugs in catalog data, as `trains_units` already does.
- The archetype gains `rally: Option<RallySpec>` beside `trains_units`, read from `structures.ron`. **Absent** on a
  structure that trains units means the default ability: one slot, `All`, no exclusion, both flags true,
  `max_waypoints` 1. That is exactly today's rule, so test archetypes built in Rust keep their behaviour unchanged
  and no number is invented in code. Every shipped producer authors the spec explicitly (WP2):

  ```ron
  // Rally (liberty AbilData:859; core AbilData:671-701): one InfoArray entry, no filter.
  // Waypoints: "up to four" (TeamLiquid 2011, plan 2026-11-25-rallies S10, verify).
  rally: Some((max_waypoints: 4, slots: [(label: "Set Rally Point")])),
  ```

  and on the three Hatchery analogues:

  ```ron
  // RallyHatchery (liberty AbilData:885-897): InfoArray 0 for non-workers, refusing resources
  // (NotResourcesOrEnemyTargetType); InfoArray 1 for workers, SetOnGround 0; NotQueen on both.
  // InfoArray 2 (SetValidators Failure) can never be set and is not authored.
  rally: Some((max_waypoints: 4, slots: [
      (label: "Set Rally Point", used_by: NonWorkers, excludes: ["hive_matron"], on_resources: false),
      (label: "Set Worker Rally Point", used_by: Workers, excludes: ["hive_matron"], smart_on_ground: false),
  ])),
  ```

  The implementer re-reads the rows (the Queen analogue is the `units.ron` row whose `sc2_analogue` begins
  "Queen") rather than trusting these slugs.
- **Validation** (typed `CatalogInvalidValue`, naming the field): `rally` only on an archetype that trains units;
  `max_waypoints ≥ 1`; `1 ≤ slots.len() ≤ u8::MAX`; every label non-empty; every exclusion an existing unit slug,
  with no duplicates; `auto_rally.slot` (D-4) less than the slot count.
- **Zero recompilation:** in a copy of the shipped catalog, splitting or merging the Hatchery analogue's slots,
  dropping an exclusion, or changing `max_waypoints` changes the behaviour in the same binary
  (`runtime_catalog_tests`).

### D-2. The state: one route per slot

- `sim_types` gains `RallyRoute { slot: u8, waypoints: Vec<RallyTarget> }`.
- `Entity::rally: Option<RallyTarget>` becomes **`Entity::rallies: Vec<RallyRoute>`**. Its invariants:
  - routes are sorted by `slot`, at most one per slot;
  - no route is empty;
  - `slot` is below the archetype's slot count;
  - each route holds at most `max_waypoints` targets.

  `validate_entity_invariants` (or the production invariant check that covers `rally` today) checks these and
  reports a typed invariant failure.
- **Hashed** in the same position as `rally`: the route count, then per route its `slot` (u8), its waypoint count
  and each target in the existing `RallyTarget` encoding. The schema takes the **next free number at merge** (48
  on `9ae5a023`; B-208's and B-209's movement branches may take a number first). The schema doc in `checksum.rs`
  gains its line.
- `// PERFORMANCE RATIONALE:` is not needed: an empty `Vec` does not allocate, routes are written only by
  commands and the auto-rally, and no per-tick path walks them.

### D-3. Setting a rally: `SetRally { target, slot }`

- `UnitOrder::SetRally` gains `#[serde(default)] slot: Option<u8>`. `None` is the right click (the smart command);
  `Some(i)` is the card's slot entry. Older bundles stay readable.
- **Target admission** (once per command), as today but with a broader unit rule:
  - `Point` on the map;
  - `Node` on the map;
  - `Unit`: exists and is alive. WP1 to WP3 keep "and the player's own". WP4 accepts any player's unit (D-6).

  Visibility is not checked, as for `AttackTarget` (T13).
- **Slot choice, per capable recipient** (its archetype's spec, or the default of D-1):
  - `Some(i)`: slot `i` if it exists and its set rule accepts the target. The set rule: a `Node` needs
    `on_resources`, and anything else is accepted.
  - `None`: the first slot whose set rule accepts the target and, for a `Point`, has `smart_on_ground` (§2.2 rule
    3).
  - No such slot: this recipient does not take the command. That is the game's `ToSelection` rule, as for plain
    orders, not a failure.
- **Writing.** Without `queue`, the slot's route becomes `[target]`. With `queue` (Shift), the target is
  appended when the route has fewer than `max_waypoints`. A full route does not take it (B-215, D-5), and an empty
  route is set as if without Shift. A target equal to the recipient itself clears the chosen slot's route, with or
  without Shift, as today.
- **Errors** (typed `GameCommandError`): the selection's own; `NoCapableProducer` when no recipient can rally;
  `RallyOutsideMap`, `InvalidRallyTarget`, `UnknownResourceNode` as today; **`NoRallySlotTakes`** (new) when
  capable recipients exist but none has a slot that takes the target; **`RallyWaypointsFull`** (new) when every
  taking recipient's slot is full.

### D-4. The slot a new unit uses, and the auto-rally's slot

- `rally_slot_for(producer, product) -> Option<u8>`: the first slot of the producer's spec whose `used_by` accepts
  the product (`Workers` when the product has a `HarvesterSpec`, `NonWorkers` when it does not, `All` always) and
  whose `excludes` does not name it. `None` means the product uses no rally (the Queen analogue on a Hatchery
  analogue). An empty chosen slot gives no order; there is no fall-through (§2.2 rule 2, B-217).
- `AutoRallySpec` gains `#[serde(default)] slot: u8`, the slot the auto-rally fills (S7). The Hatchery analogues
  author `slot: 1`; every other town hall keeps the default 0.
- `rally_point(producer)` becomes `rally_point(producer, slot)`, which resolves the slot's **first live**
  waypoint. The exit order (`production_exit`, which has the product) reads the product's slot. With one slot and
  one waypoint this is exactly today's point, so every exit outside a Hatchery analogue is unchanged (P-3).

### D-5. Waypoints and the new unit's orders

At the spawn, `give_rally_order(producer, child)` reads the child's slot (D-4) and that slot's route:

1. **Prune.** Remove every `Unit` waypoint whose unit is dead or gone (S10 posts 1 and 35, S11). If the route is
   now empty, remove it and give no order ("as if there'd never been a rally point", S9). A carried unit's
   waypoint stays, but gives no order this time (today's rule).
2. **Issue.** For each remaining waypoint in order, issue the order it means through the admission a player's order
   takes, with `queue = false` for the first order issued and `true` after it:

   | Waypoint | Child | Order |
   |---|---|---|
   | `Point(p)` | any | `Move { p }` |
   | `Node(n)` | `admit_harvest` accepts | `Harvest { n }` |
   | `Node(n)` | otherwise | `Move { node centre }` |
   | `Unit(u)` of the child's player | `admit_load` accepts | `Load { u }` |
   | `Unit(u)` of the child's player | otherwise | `Move { u's position now }` (B-163 stays: no follow order) |
   | `Unit(u)` of another player (WP4) | `takes_plain_order` accepts `AttackTarget` | `AttackTarget { u, Explicit }` (D-6) |
   | `Unit(u)` of another player (WP4) | otherwise | `Move { u's position now }` (Q0105's rule, B-187) |
   | `Unit(u)` carried | any | none; the waypoint stays |

   A refused order is skipped, so the next waypoint's order becomes the first issued. An invariant failure is
   reported as a `SimulationDiagnostic` and ends the issuing. The module doc states this rule, so it is not a
   silent path.
3. Orders after a `Harvest` are still queued, and the harvest never ends, so they never run. This is what the game
   does with a route that ends in minerals (S10 post 25). No special case is added.

`max_waypoints` caps the loop, so the spawn costs O(cap) admissions. No allocation is needed: the route is read
by index, and pruning uses `Vec::retain` on the producer's route.

### D-6. A rally on an enemy unit (B-166)

- Admission accepts another player's live unit (D-3).
- The child takes `AttackTarget { origin: Explicit }` when it can attack the target (S11). That is the player's
  own admission rule, `takes_plain_order`'s `AttackTarget` arm (T13), extracted into a `pub(crate)` helper taking
  `(player, unit, order)`, so the rally and the command share one rule without building a `PlayerCommand`. That
  file is `world/commands.rs`, not `movement/`.
- A child that cannot attack the target moves to where it stands now. This follows Q0105's default for an
  unattackable A-click target and is the same snapshot rule as a friendly unit (B-163 and B-187, open).
- **The view must not leak the enemy.** `PlayerView::rallies` publishes an enemy waypoint only while the viewer
  sees that unit (the view's existing visibility test for enemy entities). Otherwise that waypoint is omitted, and
  the line skips it. The exit order and the child's `Move` read the true position. That is simulation state, and
  in the game the produced unit also reacts to where the unit really is [INF].
- The enemy's death prunes the waypoint (D-5).

### D-7. The player view

`RallyView` gains `slot: u8` and `index: u8`. The view publishes one entry per waypoint that resolves to a point
(a live unit, uncarried, and for an enemy, seen), sorted by `(entity, slot, index)`. `point` stays `[f32; 2]`
presentation output (charter §3.2).

## 5. Determinism and checksum

- **Integer only.** Slot choice is a scan in slot order. Waypoints are processed in stored order. Distances (the
  exit order) are unchanged raw fixed point. The client's click point enters through `sim_point`.
- **Order.** Admissions run in bundle order and recipients in selection order. Routes are sorted by slot and keep
  their insertion order within one. Nothing iterates an unordered container.
- **Hashed state:** D-2, schema next free at merge. The goldens are re-recorded **once, in WP1, by bytes only**:
  - With `Entity::rallies` encoded as the old `Option<RallyTarget>` of slot 0's first waypoint, and the schema
    number unchanged, WP1's tree reproduces every recorded checksum of both goldens on all four builds.
  - Then the new encoding and schema go in, and the new checksums are recorded under a header "Re-recorded for plan
    2026-11-25-rallies WP1 (checksum schema N−1 -> N): each entity's rally becomes its routes (slot, waypoints). No
    behaviour changed: with the old encoding of slot 0's first waypoint, every checkpoint stays as recorded."
  - Builds: native debug and release, and `wasm32-wasip1` release and debug
    (`CARGO_TARGET_WASM32_WASIP1_RUNNER="wasmtime --dir=<real tree path>"`).
  - `DEFAULT_SANDBOX_CHECKSUM` and the schema-byte tests move with it.
- **After WP1 the goldens do not move.** Their halls are `foundry_core_dome`, whose auto-rally stays in slot 0, and
  no fixture issues a rally (T15). A golden move after WP1 is a stop (§8).
- **wasm.** No new dependency; the simulation crates still build for `wasm32-unknown-unknown`.
- **Cost.** Setting a rally is O(slots + waypoints) per recipient. A spawn is O(cap) admissions. The view adds one
  entry per waypoint. Per tick, nothing new runs. The throughput bench produces nothing, so it must stay
  ≥ 50 ticks/s in every scenario (measured in WP3 and WP6 against WP0's figures).

## 6. Acceptance (principled properties, fixed before implementation)

Every property below is a property of the rule, tested on constructed worlds that read slots, caps, costs and
times from the catalog, never a seed's figure.

- **P-0 (probe, WP0).** On WP0's tree, the commands of `~/scratch/resource-footprints/scripts/measure.sh` (the

  6,000 ticks) and the skirmish match must show:
  - zero `SetRally` commands issued;
  - zero units produced by a Hatchery analogue;
  - zero units produced with a rally.

  The probe is a temporary counter in a scratch copy, not committed. Its result is in the evidence. If any count is
  non-zero, §7's prediction is rewritten from the trace before WP1.
- **P-1 (state).** Each route's invariants hold after every tick of every rally test. The encoding of `rallies`
  changes the checksum when a slot, a waypoint or a target changes (`checksum_state_tests`).
- **P-2 (slots).** On the Hatchery analogue:
  - a right click on a field sets the worker slot;
  - one on the ground, or on a unit, sets the army slot;
  - the worker entry on the ground sets the worker slot;
  - the army entry on a field is refused (`NoRallySlotTakes`);
  - a worker uses the worker slot, the Overlord analogue the army slot, and the Queen analogue none;
  - the auto-rally fills the worker slot only.

  On every other producer, everything behaves as on WP1's tree.
- **P-3 (no change without slots or waypoints).** A producer with one slot and a single-waypoint rally gives the
  same order and the same exit cell as on WP1's tree, for every row of the production plan's D-4 table.
- **P-4 (waypoints).**
  - Shift appends up to `max_waypoints`, after which the append is refused (`RallyWaypointsFull`).
  - The child's order queue equals the waypoints' orders in order, the first replacing and the rest queued.
  - A dead unit waypoint is pruned, and the child goes to the next one.
  - All waypoints dead: no order, and the route is gone.
  - A route ending in a field leaves a worker harvesting it after walking the earlier points.
- **P-5 (enemy).**
  - A rally on an enemy unit stores `Unit(enemy)`.
  - A child that can attack it has `AttackTarget { enemy, Explicit }` as its order on its spawn tick, and one that
    cannot has `Move` to the enemy's position.
  - The enemy's death prunes the waypoint.
  - The view omits the enemy's waypoint while the viewer does not see it.
- **P-6 (integration through `PlayerCommand`).** One test drives everything through `TickBundle`s only:
  - a Hatchery analogue and a Barracks analogue;
  - right clicks and Shift-right-clicks as `PlayerCommand { order: SetRally { .. }, queue }`;
  - a worker, an Overlord analogue and a Queen analogue trained at the Hatchery analogue, and two soldiers at the
    Barracks analogue, one of them rallied through a point to an enemy unit.

  It asserts each child's order queue on its spawn tick and, 200 ticks later, the worker harvesting, the soldier
  attacking, and the Queen analogue idle where it left.
- **P-7 (worlds).** §7.
- **P-8 (throughput).** Every bench scenario ≥ 50 ticks/s in release, and no scenario more than 3 % slower than on
  WP0's tree (noise band).

## 8. Stop rules

1. **P-0 finds a rally or a Hatchery analogue product in a measured world.** Stop before WP1 and rewrite §7 from
   the trace (orchestrator).
2. **WP1 is behaviour-neutral.** Only the checksums move, and the §5 proof holds on all four builds before the
   re-record. Any other difference stops the package.
3. **Any measured world moves** in any package (§7's byte-identical rows). Stop, with the first differing tick and
   entity, to the orchestrator.
4. **A golden moves after WP1.** Stop: a fixture acts on a rally, which T15 says none does.
5. **WP2 changes only Hatchery-analogue products and the slot-aware admission** (P-2, P-3). An existing test that
   fails outside `rally_tests.rs` and the tests §11 lists is a finding and stops the package.
6. **Throughput below 50 ticks/s** in any bench scenario, or more than 3 % slower than WP0 in one. Stop with the
   profile.
7. **No tuning constant.** The cap and slots are data, and the orders follow the stated rules. An implementer who
   needs a number not in §2.3 stops and asks.
8. **The skirmish match** wins within its `TICK_LIMIT`, stage for stage as on WP0's tree. If not, stop with the
   trace.
