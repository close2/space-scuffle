# Round48: paid, capability-driven construction lifecycle

Status: planning only; requires orchestrator review and explicit implementation release. This is a separate game feature after43 production,45 movement and38 command/tick interfaces stabilize. It is not bundled into47 or38. No editor, map-authoring tool or substitute media work is authorized.

## Goal and verified current defects

A Build command must select an authorized owned builder, approach a legal site, create one paid vulnerable foundation, advance the authored construction process, and enable the completed structure exactly once. Cancel, worker loss, damage, destruction, blocked placement and queued orders must preserve resources, identity, occupancy and43's captured supply ledger.

Current `world.rs::process_commands` calls `spawn_structure` for Build and discards the result. It does not inspect recipients, builder capability, costs, prerequisites, range or time. `spawn_structure` is intentionally a free **completed setup** transaction; using it for player commands grants immediate health, supply and capability. Keep its setup/scenario contract, but remove every Build-command route to that API.

The catalog already contains costs, `build_time_ticks`, footprints, prerequisites, supply and optional harvester/other capabilities. Harvesting is not proof of building permission. There is no builder capability or construction runtime state; `Entity::from_archetype` marks all inserted entities completed. `is_completed` alone does not currently gate every weapon/detector/dropoff/ability consumer. Snapshot progress exists as `build_or_queue_progress` but the writer supplies None. Three authored workers have harvesting capability; structures include new construction, upgrades/morphs, resource extractors and lore describing unimplemented power/creep. Those distinctions must become explicit data, never unit-name or faction branches in Rust.

`GameMap::can_place_building` checks footprint, bounds, buildability, ramps, existing structure occupancy and uniform cliff level. It does not check mobile unit overlap, natural resources, neutral towers, builder reach or current vision. `place_structure` changes ground pathability and registers footprint ownership. `remove_structure` assumes valid registered bounds/cell ownership and restores buildable/pathable flags.43 already supplies safe lifecycle preflight; reuse its prepared removal invariant. A construction site must additionally require originally pathable/buildable terrain, so removal cannot manufacture pathability on a previously nonpathable cell. Wider terrain restoration semantics require a separate reviewed map-core change, not editor changes.

## Declarative schema and compatibility

Add optional `BuilderSpec` to the existing capabilities bundle as the single new authority; do not duplicate it as another top-level convenience field. The authored definition contains an explicit list of structure slugs, fixed-point work range in world units, and participation mode: `Attached`, `AutonomousAfterStart`, or `ConsumedAtStart`. Resolve slugs to catalog IDs only after the entire external unit/structure bundle loads. No permission is inferred from faction, harvesting, display name or shape alone. Range is measured from the builder's collision-circle edge to the nearest point of the footprint rectangle, with a connected unobstructed work corridor; it is not center-to-center range.

Add optional `ConstructionSpec` to actual directly constructible structure definitions. It contains placement rule, initial hull/shield fractions, construction vision radius, under-construction hull/shield armor (authored zero for the referenced rule), cancel refund fraction as checked integer numerator/denominator, and any mode compatibility restriction. Reuse existing duration/cost/footprint/prerequisite fields rather than duplicate sources. Normal structure operational stats remain unchanged. All ongoing task values that affect later behavior are captured in task state, including prices paid and refundable ratio; catalog edits cannot retroactively change refunds or supply.

Supported placement rules are `BuildableGround` and `OnResourceNode { kind }`, with explicit exact resource-center/footprint alignment. Current maps expose resource nodes without an additional ground reservation format, so identify them by checked map-local resource index plus the captured cell/kind/position signature and preserve them when claiming a site. `ResourceNode` has no entity ID; the current map exposes a fixed-length resource slice, not insertion/removal APIs. A resource-specific foundation records the claimed node; another claim rejects. Construction does not consume the natural node. Ordinary buildings reject overlap with resource/tower occupied cells; an extractor exempts only its matched resource node. Do not use lore's gas-extractor flag as a string-based exception. Require an explicit construction placement rule for every authored extractor admitted to this workflow.

Data-only migration explicitly lists permitted directly constructible products on each intended builder. Upgrade/morph/add-on definitions lacking this construction capability remain unavailable to Build with a typed workflow rejection; they are not silently created as new buildings. Do not infer the lists by shared faction. The schema permits different authored participation modes without compilation. No power/creep coverage system exists today: this round uses explicit declared placement rules without pretending SPEED_ZONE is creep or inventing a power radius. If such requirements are desired, they require their own authored capability/coverage blueprint before being enabled; this round makes no parity claim for them.

Validate duplicate/dangling references, nonstructure products, zero/negative/unrepresentable ranges, invalid fraction denominators/ranges, nonpositive initial hull, footprint conversion/bounds, impossible supply/refund arithmetic and placement/mode incompatibility in the real loader. Missing optional builder means no construction permission. Missing construction specification means another workflow, not a permissive default. Update the real selected RON files and complete-bundle serialization/validation fixtures. Explicitly version the new catalog/lifecycle compatibility contract; do not silently deserialize an old gameplay save as a completed building.

## Worker modes and lifecycle state

`Attached`: worker stays a separate live targetable unit outside the footprint. It performs no harvesting/attacks/abilities while actively working. Death, transport, interruption, invalid range or lost capability suspends progress; the paid foundation remains vulnerable and may be resumed by one compatible owned worker. No automatic replacement worker is selected. Completed/cancelled/destroyed foundations release the worker to its next queued valid order, or Idle.

`AutonomousAfterStart`: worker starts the same paid foundation transaction, is released immediately, and may continue its queue. Foundation progress subsequently requires no worker. Later worker death must not destroy or pause that task.

`ConsumedAtStart`: use an explicit identity-preserving transformation of the builder into its foundation, retaining its EntityId and a captured return-state record within the construction task. Do not simulate consumption by killing a worker, emitting shatter, or refunding its unit cost. Release its captured mobile supply and provider contribution and replace them with foundation captured usage in the same checked ledger transaction; no half-updated ledger is visible. Clear navigation/weapon/transport state for the foundation. Only an untransformed eligible mobile builder may enter this mode, preventing recursive retained construction state. A queued consumed request is terminal for that worker: reject attempts to append commands behind it explicitly rather than silently dropping them after morph.

The return record preserves catalog identity, effective vitals and actually implemented worker status required for deterministic restoration; nonexistent cargo/research state must not be assumed. it is authoritative checksum state, not a client clone. Original action queues are not replayed on cancel. Restore as Idle with the same identity and a health/shield fraction no greater than both the retained worker's fraction and the damaged foundation's current fraction, using exact widened ratios and a positive live hull minimum only for a still-living foundation. Never restore a dead foundation's worker. These are explicit project rules requiring approval, not asserted exact SC2 cancellation semantics.

Cancellation restoration must have a legal actual45 endpoint and collider clearance after the proposed footprint removal. Prefer the former foundation center if valid, then a finite deterministic connected perimeter; never spawn remotely or overlap another unit. If no legal restoration position exists, retain the foundation and paid task with a typed CancellationBlocked status, no partial refund/removal; retry the request until legal or until the player changes the request. Destruction while awaiting cancellation destroys the contained worker and refunds nothing. This deliberately conservative cancellation policy needs explicit approval.

## Progress, damage and operational completion

Capture total work ticks and a lossless u32 completed/remaining work value. Positive N completes after N eligible work updates, including its start update if the worker is already in valid range. Zero duration still goes through the paid placement transaction and completes in its first eligible update. Paused attached work neither advances the timer nor loses the paid task. Never derive authoritative progress from elapsed client time or float animation phase.

At foundation creation, hull starts at the authored positive fraction of captured effective completed max hull; shields start at their authored fraction. Construction adds only newly earned vitality: `earned(p)=initial + floor((maximum-initial)*p/total)` using widened fixed-point/integer arithmetic. Add the difference between consecutive earned budgets to current vitality and cap at the captured maximum. Incoming damage remains damage; do not overwrite current HP with the progress curve or heal all damage on completion. Apply the same rule to shields where present. Ordinary regeneration/energy generation is disabled while incomplete unless a separately authored rule is approved. Armor comes from ConstructionSpec while incomplete and switches to normal captured/live-upgrade policy only on completion.

Run construction's work/completion phase after existing phase2 hazards have resolved and before later vision/movement/combat phases. A worker or foundation killed by those hazards cannot contribute or complete. Approach movement occurs later in the tick, so newly reaching work range first contributes on the next phase2; do not sneak a second movement/progress update into the tick. Newly completed structures can provide vision/detection and defend in later phases that tick, but production admissions happened earlier in phase1 and cannot be retroactively accepted; their training begins through the normal later eligible tick. Specify the exact call ordering beside43, which rechecks hazard-dead producers at completion.

Audit every operational consumer: training/research/prerequisites, weapons/auto-acquisition, ability casting, detection, transport and resource-dropoff require completed state. Incomplete foundations are visible/targetable/damageable obstacles with their explicit construction sight radius, not full powered structures. Suppress passive resource generation and provider supply until completion. Completion atomically marks completed, installs captured provider contribution, updates uncapped provider total/effective cap using43, removes task links, and publishes one Completed notice. Over-capacity play and provider destruction retain43's existing rules; do not refund/recharge costs or double-count supply.

## Cancel, destruction and refunds

Cancel validates player ownership and exact still-active request/foundation identity. Cancel an unpaid queued/approaching request by removing its executable reference and releasing its worker commitment; refund zero because nothing was paid. Cancel a started living foundation with `floor(paid_cost * numerator / denominator)` independently for minerals/gas, using checked widened arithmetic. Default authored structure policy is3/4, based on the cited guidance. Resource credit overflow rejects/corrupt-state diagnostic before any map, task, entity or worker change; never saturate or silently discard money. No refund is computed from current catalog prices.

Completed structures cannot be cancelled through this command. Dead foundations awaiting reap cannot be rescued for a refund. Foundation destruction uses ordinary combat/death evidence, releases captured usage and its actual registered footprint exactly once, clears builder/task references, and grants no refund. A contained worker is lost with the destroyed foundation; a separate attached worker survives unless independently killed. Cancellation is an explicit despawn/restore reason, not fake damage or combat shatter. All termination paths invalidate routes/clearance after the committed removal and preserve unaffected terrain cells and resource claims.

A second cancel, a stale task ID or a completion/cancel race produces a typed ordinary rejection and no second credit. Phase1 cancellation before that tick's later lethal damage follows normal command order; a foundation already dead at phase1 is ineligible. No world-wide transactional rollback is claimed if an unrelated later phase fails.

## Review amendment: generic builder state, map extents and consumed identity

This amendment answers the four architecture gaps identified by the orchestrator. These are proposed explicit policies requiring review; they do not authorize construction implementation or expand38/45.

### Reservations and operational state are never discarded

A builder archetype may expose other capabilities. `ConsumedAtStart` admission and start both reject a nonempty paid `production_queue` with an ordinary Busy reason. Do not silently cancel those jobs, move their reserved supply into the foundation, or refund them through construction. This includes jobs that were added while an unpaid build request approached the site. All accepted consumed starts therefore have zero production-job reservations to transfer, while their entity supply contribution is replaced atomically using43's captured ledger. A future explicit production transfer feature would require its own contract; this construction round does not need one.

Current research is an immediate player-upgrade transaction, not an entity-owned paid research queue; do not invent a queue or cancel player upgrades when a builder transforms. If timed entity research is introduced before48 implementation, its busy/reservation policy becomes an implementation prerequisite and must be reviewed explicitly, defaulting to rejection rather than dropped work. The current entity has no carried mineral/gas inventory. Likewise, no fake cargo return record is introduced; a real cargo subsystem added before48 requires preservation/rejection rules before consumed construction can be enabled.

For consumed starts require a normal completed mobile actor with no active mode/siege state, active buffs/debuffs, pending ability or channel, cloak or invulnerability. Revalidate after approach. Reject busy state rather than cleanse it by transformation. Retain current energy, hull/shields and effective maxima, ability cooldowns, weapon cooldown, damage-regeneration delay and captured supply. A carried buff cannot be frozen and replayed because admission rejects it. Existing cooldowns continue to elapse by authoritative construction ticks; they are not reset to ready on cancellation. No energy or vitality regeneration accrues in the return record. Committed outgoing projectiles/hazards remain independent existing authoritative effects with their original source identity, not cancelled, cloned or refunded by construction. Pending windup is cancelled before foundation creation under the ordinary interrupt contract, without producing damage or resetting an existing cooldown.

For `Attached`, the worker remains the same live entity and retains every reservation. Already-paid production continues through43's normal phase while construction progresses; its completion placement still considers the new foundation and actual occupancy. New Produce/ability/attack/harvest orders detach the worker only after those commands pass their ordinary admission checks; rejected commands do not interrupt paid construction. Existing buffs, cooldowns and damage state continue their ordinary simulation updates. A builder already channeling cannot start work until that operation finishes or an explicitly accepted interrupt occurs. Active construction suppresses weapon acquisition/firing and harvesting but does not erase state. Worker death follows the ordinary reap path for its production reservations/supply and separately detaches the construction link. Autonomous workers retain all their state and resume the queue after the successful start transaction.

**Transport prerequisite uncovered by actual source review:** `load_unit_into_transport(unit_id, _transport_id)` currently ignores the carrier identity and only sets a passenger boolean. Therefore the current world cannot prove that a would-be consumed builder carries no passengers; archetype lore or lack of a transport capability is not proof because this public API accepts any carrier ID. Consumed construction must not ship on that unprovable assumption. Before enabling `ConsumedAtStart`, introduce/review authoritative passenger→carrier identity and inverse-query validation as a separately staged dependency, preserving45's checked unload endpoints. Admission then rejects both loaded builders and builders with any registered passengers. Do not use a global “any transported unit blocks every builder” workaround or mutate arbitrary passengers on transformation. Attached loading is an accepted interruption only through that actual transport lifecycle. This prerequisite is a scope decision for the orchestrator, not authorization to implement transport inside47/38.

### Explicit map-derived construction reservations

`ResourceNode` exposes `pos`, `kind`, `remaining` and `cell`; it has no physical radius or ID. Define the node's construction reservation as exactly its existing half-open unit grid cell `[cell.x, cell.x+1) × [cell.y, cell.y+1)`. Validate the authored cell is in bounds and corresponds to the node position under the map's cell convention. The immutable map-local index plus captured cell/position/kind identifies a claim, and changed topology/signature is a typed invalid-world condition. Depletion changes `remaining`, not claim identity. This is a construction-placement reservation rule, not a claim about rendered crystal dimensions or a new ground-movement obstacle.

`Watchtower` exposes a stable ID and position but only interaction/vision radii. Its construction reservation is the half-open unit cell containing its fixed-point position, with widened checked floor/bounds conversion. `capture_radius` and `reveal_radius` are not physical extents and must never be substituted as a collider. This one-cell reservation is an explicit project rule drawn from existing map coordinates; larger physical footprints require future authored gameplay data and a separate compatibility decision. The implementation must name and test this rule rather than pretending the map already contains a tower body radius.

Ordinary foundations reject any footprint-cell overlap with these reservations. Resource placement may exempt only its exact claimed node, while still rejecting every other node/tower reservation. The footprint center must equal the captured node position under the explicit `OnResourceNode` alignment rule; an incompatible node/footprint combination is rejected, never silently snapped. Tests use real existing maps plus fractional/boundary fixtures and distinguish reservation geometry from visual art.

### ID allocation and captured cancellation restoration

Prepared starts have distinct identity variants. A normal foundation prepares/checks a fresh `next_entity_id` and advances it only on successful commit. A consumed foundation retains the builder's ID and does not read, reserve or advance `next_entity_id`; even an exhausted new-entity allocator cannot reject an otherwise valid identity-preserving transformation. Both kinds require a new checked construction request identity, because request lifetime differs from entity lifetime. Failure before either commit leaves both allocators unchanged; tests assert this directly. Do not call a common “allocate then overwrite ID” helper for the consumed case.

At consumed start capture the worker's simulation-definition signature and explicit restoration fields: original UnitTypeId, mover layer, collision radius, effective max hull/shield/energy and current vitals, original captured supply used/provided, relevant cooldown/damage-delay state, and normal-mode identity. The signature covers all simulation-relevant fields that a restored actor would subsequently read, excluding media/lore. Cancellation validates the current definition still matches before choosing a position. If it changed or disappeared, report `CancellationBlocked::DefinitionChanged` and retain the living paid foundation/task; never validate a captured small radius and then restore a larger live-catalog body. A blocked cancellation is observable and may succeed after a valid matching definition is restored; destruction still refunds nothing.

Legal return placement uses that captured mover/radius and45's exact current map/body queries after proposed footprint removal. The supply transaction restores original captured used/provided values, releases the foundation's captured values, and checks current43 ledger arithmetic/admission rules before mutation. Refund, map removal, entity replacement and task removal form one prepared commit. An occupied endpoint, unavailable supply, changed definition or arithmetic failure cannot grant partial resources or remove the foundation.

Returned hull and shields are bounded by both the captured worker's surviving fraction and the foundation's current surviving fraction using widened exact arithmetic. Damage cannot be erased through build/cancel; a dead foundation never restores anything. The returned worker keeps its original owner/ID, gets no free energy or fresh cooldowns, and resumes Idle without replaying old requests or abilities. Elapsed retained timers never underflow. Any future timed status introduced into Entity must be enumerated in this captured policy or explicitly make consumed admission unsupported until covered; generic whole-entity cloning is not a substitute for reviewed lifecycle semantics.

### Narrow transport-identity prerequisite blueprint scope

This prerequisite is planning only, not construction implementation authorization. Its goal is a trustworthy answer to “is this actor carried, and does this actor carry passengers?” with complete link cleanup. It does not add player transport commands, boarding AI/range, cargo capacity, authored transport creatures, passenger firing or transport media. The existing low-level world helper is an embedding/setup operation; adding a validated carrier reference must not be advertised as a complete capability-driven transport game feature.

Use one authoritative passenger-side `Option<EntityId>` carrier reference, replacing the existing freely mutable `is_loaded_in_transport` boolean. Provide read accessors such as `transport_carrier()` and `is_loaded_in_transport()`; all combat, vision, movement, snapshot and production readers derive loaded state from the reference. Do not retain two writable sources that can disagree. Store no duplicate authoritative passenger Vec on the carrier: deterministic entity iteration can answer `has_passengers(carrier)` for rare load/morph/lifecycle operations; an optional inverse index would be derived and justified only by measured need. Exclude nested transport initially: a passenger cannot be a carrier with passengers, and a carrier cannot itself be loaded. This makes cycle prevention local and explicit.

Introduce a typed `try_load_unit_into_transport(passenger, carrier)` transaction; retain the old bool wrapper only as a clearly documented compatibility adapter if required by callers. Validate both identities exist, differ, are alive/completed and have valid owners; they must share the same actual owner. Reject an already-loaded passenger, a loaded carrier, a passenger currently carrying other entities, a registered foundation passenger, or a passenger with paid production jobs. Last restriction preserves43 reservations without inventing production-in-cargo behavior. Channeling/pending abilities require an explicit safe interruption policy; the narrow initial rule is a typed Busy rejection. No order clearing or ledger mutation occurs until every check passes. On commit, set the sole carrier reference and retain the current ordinary load effects (clear navigation/orders/target and zero velocity). Do not reset HP, energy, buffs, cooldowns, captures or supply.

Unload continues through45's exact `validate_displacement_destination` and shared footprint/body checks. Require an existing valid live carrier reference before preparing the endpoint. On success clear the reference and place the passenger at precisely the validated point, with current45 velocity/order/waypoint clearing; on failure preserve link, entity position, orders, economy and checksum. No fallback point search, teleport through a cliff or invisible ejection is introduced here. Subsequent requested gameplay boarding/unloading range and capacity need a separate authored capability blueprint.
